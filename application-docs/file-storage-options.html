ทางเลือกการเก็บไฟล์ — Profile & Attachments

สรุป solution สำหรับเก็บรูปโปรไฟล์ (และเตรียมทางสำหรับ screenshot แนบเคสในอนาคต) ในบริบท IT Helpdesk: Nest API + Next.js + PostgreSQL บน intranet

Use case แรก: avatar ขยายได้: ticket attachments เป้าหมาย: ง่ายตอนนี้ · ย้ายคลาวด์ทีหลังได้

1. หลักการที่ไม่ควรละเลย

  • แยก metadata กับ binary — Postgres เก็บ “ไฟล์คืออะไร / ใครเป็นเจ้าของ”; เนื้อไฟล์อยู่นอก DB
  • อย่าเก็บรูปเป็น base64 ใน JSON/DB — บloat, backup ช้า, query ช้า
  • URL ที่ client ใช้ไม่ควรเป็น path จริงบนดิสก์ — ผ่าน API หรือ signed URL
  • ตรวจชนิด/ขนาดตอนอัปโหลด — MIME allowlist, max size, (ทางเลือก) strip EXIF
  • ตั้งชื่อ object ด้วย id ที่ไม่เดา — เช่น avatars/{userId}/{cuid}.webp

2. ตัวเลือกหลัก (เปรียบเทียบเร็ว)

แนะนำเริ่มต้น

A. Local disk / Docker volume

เขียนไฟล์ลงโฟลเดอร์บนเครื่อง API (หรือ volume ใน Compose)

  • ตั้งเร็วมากสำหรับ intranet
  • backup = volume + DB
  • ขยายหลาย instance ยาก (sticky / shared NAS)
แนะนำระยะกลาง

B. S3-compatible (MinIO → S3/R2)

ใช้ API แบบ S3; ตอน dev รัน MinIO ใน Docker เดียวกับ Postgres

  • โค้ดชุดเดียวกับ production object storage
  • scale / CDN / lifecycle ได้
  • ต้องดูแล bucket + key + policy
ไม่แนะนำ

C. เก็บใน PostgreSQL (BYTEA)

ใส่ binary ลงแถวใน DB

  • ดูง่ายตอน demo เล็ก ๆ
  • backup / replication พอง
  • ไม่เหมาะกับรูปจำนวนมาก
เกณฑ์ Local volume MinIO / S3 BYTEA ใน Postgres
ความเร็วในการเริ่ม เร็วสุด ปานกลาง เร็ว (แต่ติดกับดัก)
ย้ายขึ้น cloud ภายหลัง ต้องย้ายไฟล์ + เปลี่ยน adapter เปลี่ยน endpoint/bucket ยาก / ไม่คุ้ม
หลาย API instance ต้อง shared storage ดีโดยธรรมชาติ ใช้ได้ แต่ไม่ใช่เหตุผลพอ
ต้นทุน ops (intranet) ต่ำ ต่ำ–กลาง (MinIO ใน Compose) ซ่อนใน DB
เหมาะกับ avatar + ticket file ดีสำหรับ MVP ดีที่สุดระยะยาว ไม่เหมาะ

ทำไมไม่กระโดด MinIO ทันที?

Avatar ตอนนี้ปริมาณน้อย และทีมยังโฟกัส domain อื่น — Local เร็วกว่าและไม่เพิ่ม service แต่ถ้าข้ามไป MinIO ตั้งแต่แรกก็ได้ถ้าอยากล็อกสัญญา S3 ตั้งแต่ต้น (trade-off: compose ซับซ้อนกว่านิด)

สัญญา StoragePort (ตัวอย่าง)

interface StoredObject {
  key: string           // avatars/{userId}/{fileId}.webp
  contentType: string
  byteSize: number
}

interface ObjectStorage {
  put(key: string, body: Buffer, contentType: string): Promise<StoredObject>
  getStream(key: string): Promise<Readable>
  delete(key: string): Promise<void>
  // optional later:
  // getSignedUrl(key: string, expiresSec: number): Promise<string>
}

คงฟิลด์ users.avatarUrl เป็น URL ที่ฝั่งเว็บเรียกได้ (เช่น /api/files/{id} หรือ public path ภายใต้ CDN) หรือชี้ avatarFileId แล้วให้ presenter สร้าง URL

5. Flow อัปโหลด Avatar (ควรเป็นแบบนี้)

  1. Client ส่ง multipart/form-data → POST /api/users/me/avatar (JWT)
  2. API ตรวจ MIME (image/jpeg|png|webp) และขนาด (เช่น ≤ 2–5 MB)
  3. (แนะนำ) แปลง/ย่อเป็น WebP สี่เหลี่ยมจัตุรัสด้วย sharp — ประหยัดที่เก็บ + โหลดเร็ว
  4. บันทึกผ่าน ObjectStorage.put + insert metadata
  5. อัปเดต users.avatarUrl / avatarFileId; ลบไฟล์เก่า (soft หรือ hard ตาม policy)
  6. Client แสดงรูปจาก URL ใหม่ (+ cache-bust query ?v=updatedAt)
อย่า ให้ Next.js เขียนไฟล์ขึ้น disk ของ web container โดยตรงถ้า API เป็น source of truth — อัปโหลดผ่าน API จะคุม auth / validation / storage ให้ที่เดียว

6. ทางเลือก “เด็ด” อื่นที่คุ้มรู้ไว้

Presigned upload (S3)

API ออก URL ชั่วคราว → browser อัปโหลดตรงเข้า bucket → callback/confirm metadata ลดโหลดบน Nest เมื่อไฟล์ใหญ่ (เหมาะ ticket video/screenshot เยอะ)

Cloudflare R2 / AWS S3 / Azure Blob

Production นอก intranet หรือต้องการ CDN สากล — ใช้ adapter เดียวกับ MinIO (S3 API หรือ SDK เฉพาะค่าย)

Image CDN / imgproxy

เก็บต้นฉบับอย่างเดียว แล้วให้บริการหลายขนาด (64 / 128 / 256) ผ่าน query — avatar ใน header จะลื่นมาก

Antivirus / ClamAV (optional)

ถ้าเปิดให้แนบไฟล์หลากชนิดจากพนักงานทั่วไป — สแกนก่อนเก็บ สำหรับ avatar อย่างเดียว มักพอด้วย MIME + re-encode

7. ข้อเสนอตัดสินใจ (สำหรับคุยรอบถัดไป)

คำถามค่าที่แนะนำตั้งต้น
Storage เฟส 1 Local volume apps/api/uploads + Docker volume
Storage เฟส 2 MinIO ใน Compose → ย้าย R2/S3 ได้โดยไม่เปลี่ยน use case
รูปแบบรูป รับ JPEG/PNG/WebP → แปลงเป็น WebP ก่อนเก็บ
ขนาดสูงสุด (avatar) 2 MB ต้นทาง / เก็บที่ ~256–512 px
การเข้าถึง JWT สำหรับอัปโหลด; อ่าน avatar เป็น public-ish intranet URL หรือ signed ถ้าต้องการเข้ม
ลบ user (soft delete) เก็บไฟล์ไว้หรือ GC ทีหลังด้วย job — อย่าลบทันทีถ้า ticket ยังอ้างอิง

เมื่อตกลงเฟส 1 แล้ว งาน implement ถัดไปคือ: ObjectStorage port + Local adapter + POST /users/me/avatar + ต่อปุ่มเปลี่ยนรูปใน Profile

เอกสารนี้เป็นทางเลือกและข้อเสนอ — ยังไม่ผูก implementation จนกว่าจะเลือกเฟส 1 (Local) หรือกระโดด MinIO ตั้งแต่แรก
