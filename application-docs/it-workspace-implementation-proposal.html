1. บทสรุปและปัญหาปัจจุบัน

หน้า /[locale]/it คือ กระดานติดตามงาน IT (Kanban) ปัจจุบัน UI ค่อนข้างครบตามดีไซน์ แต่ข้อมูลและแอ็กชันส่วนใหญ่ยังเป็น mock ใน browser — ไม่ได้อ่าน/เขียน Ticket จาก PostgreSQL

สิ่งที่ทำได้จริงแล้ว (นอกกระดาน) Guest แจ้งปัญหาผ่าน portal → POST /tickets/report บันทึก Ticket + รูปแนบลง DB แล้ว
สิ่งที่กระดานยังไม่ทำ รายการการ์ด, Claim, Resolve, Quick Log, Timeline, โน้ต, โอนงาน, ผู้ร่วมเคส — ยังไม่ผูก API
ผลกระทบตอนนี้: หลังส่งแจ้งปัญหาแล้วกดไปหน้ากระดาน IT จะไม่เห็นเคสจริง เพราะกระดานยังอ่านจาก mockKanbanTickets

เอกสารนี้เสนอ แนวทาง implement ที่ยึด UI ปัจจุบันเป็น contract ของฟีเจอร์ และยึดกฎโดเมนจาก CONTEXT.md + ADR 0001 (Work Cycle), 0002 (Guest/IT), 0003 (Email close/reopen)

5. Solution ที่เสนอ

5.1 หลักการออกแบบ

  1. Board = projection ของ Ticket ในรอบงานปัจจุบัน ไม่ใช่ state คนละชุดกับ DB
  2. Guest อ่านได้อย่างเดียว; ทุก write ต้องมี IT JWT
  3. แยกสถานะปฏิบัติการของ IT กับ Closed Ticket หลัง user ยืนยัน (ADR 0003)
  4. ทำทีละเฟส: ให้เคสจาก portal โผล่บนกระดานและ claim/resolve ได้ก่อน แล้วค่อยครบ timeline / quick log / work cycle
  5. คงเลย์เอาต์ UI เดิมให้มากที่สุด — เปลี่ยนแหล่งข้อมูลและทำให้ปุ่มมีผลจริง

5.2 ทางเลือกสถาปัตยกรรม (ขอเลือกทิศ)

ทางเลือกรายละเอียดข้อดีข้อเสีย
A — Lean board first (แนะนำ) เฟส 1 ใช้ Ticket + Assignee + Attachment ที่มีอยู่; map คอลัมน์แบบ pragmatic; Worklog ใช้เป็น timeline พื้นฐาน เร็ว, เห็นเคสจริงเร็ว, เสี่ยงต่ำ ยังไม่ครบ ADR work cycle / email close ในเฟสแรก
B — Domain-complete first สร้าง WorkCycle + ConfirmToken + status ใหม่ทั้งหมดก่อนค่อย wire UI ตรงโดเมนระยะยาว ช้า, อั้นมูลค่าจากเคส portal ที่ค้างใน DB
C — Hybrid Lean board + ออกแบบ schema ให้รองรับเฟสถัดไป (nullable workCycleId, event log) สมดุล ต้องวินัยไม่ทำ half-feature
คำแนะนำของผู้เขียนเอกสาร: เลือก C (Hybrid) — ส่งมอบกระดานใช้งานได้เร็ว แต่ไม่บล็อก ADR ในภายหลัง

6. การแมปสถานะคอลัมน์ (จุดที่ต้องตัดสินใจ)

UI มี 4 คอลัมน์ แต่ Prisma มีสถานะ: OPEN, IN_PROGRESS, PENDING_APPROVAL, RESOLVED, CLOSED

6.1 ข้อเสนอ Mapping ชั่วคราว (เฟส 1)

คอลัมน์ UIสถานะ DB ที่เสนอเงื่อนไขเพิ่ม
backlogOPENยังไม่มี assignee หรือเพิ่งเข้าคิว
in_progressIN_PROGRESSมี assignee อย่างน้อย 1 คน
pending_userPENDING_APPROVAL หรือ RESOLVEDต้องตกลงความหมาย — ดูคำถาม Q3
resolvedCLOSED (ระยะยาว) / ชั่วคราวอาจโชว์ RESOLVEDADR: CLOSED หลัง user confirm
ศัพท์ที่สับสน: ใน UI คอลัมน์ชื่อ “resolved” แต่ในโดเมน “Closed Ticket” หมายถึงปิดถาวรหลัง user ยืนยันอีเมล แนะนำให้แยกป้ายในผลิตภัณฑ์ชัด เช่น IT กด “ส่งให้ผู้ใช้ยืนยัน” ≠ “ปิดเคสถาวร”

8. Workflow หลัก

8.1 Standard ticket (จาก Portal → กระดาน)

flowchart TD A[Guest กรอกฟอร์มแจ้งปัญหา] --> B[สร้าง Ticket type STANDARD\nstatus OPEN] B --> C[โผล่คอลัมน์ Backlog] C --> D{IT Claim?} D -->|ใช่| E[status IN_PROGRESS\nเพิ่ม Assignee] E --> F[ทำงาน / เขียน Worklog] F --> G{พร้อมให้ user ตรวจ?} G -->|ใช่| H[ย้ายไป Pending User\nส่งอีเมลยืนยัน - เฟสถัดไป] G -->|ยัง| F H --> I{User ยืนยัน?} I -->|Close| J[CLOSED = Closed Ticket] I -->|Reopen| K[กลับ IN_PROGRESS\nอยู่รอบที่ reopen] J --> L[รอ Work Cycle Close\nเข้า Ticket History]

8.2 Claim / เปลี่ยนผู้รับผิดชอบ

  • Claim จาก backlog: ผู้ล็อกอินกลายเป็น assignee (lead ถ้าเป็นคนแรก)
  • เพิ่ม collaborator: IT คนอื่นถูกเพิ่มใน TicketAssignee
  • Transfer: เปลี่ยน lead / ย้ายความรับผิดชอบ (ต้องนิยามสิทธิ์)

8.3 Quick Log (งานหน้างานจบเร็ว)

flowchart TD Q1[IT เปิด Quick Log] --> Q2[กรอกแผนก/อาการ/วิธีแก้] Q2 --> Q3[สร้าง Ticket type QUICK_TICKET] Q3 --> Q4{นโยบายอนุมัติ?} Q4 -->|ต้อง Supervisor/Manager อนุมัติ| Q5[QuickTicketApproval PENDING] Q4 -->|อนุญาตปิดเองได้| Q6[เข้าสถานะตามที่ตกลง] Q5 --> Q7[ผู้อนุมัติ Approve/Reject]
Quick Log ใน UI ตอนนี้ไม่สร้างอะไรเลย — ต้องตัดสินใจว่าเคสเหล่านี้ขึ้นกระดานชั่วคราวหรือเข้าประวัติทันที

8.4 Work Cycle Close (ADR 0001 — เฟสหลังกระดานใช้ได้)

  • ตัดรอบอัตโนมัติทุก 2 สัปดาห์
  • เฉพาะ Closed Ticket ออกจากกระดานเข้า Ticket History
  • งานไม่จบ = Carryover ไปรอบใหม่ พร้อมแท็ก Origin Cycle

11. แผนงานแบ่งเฟส (แนะนำ)

เฟสส่งมอบคำนิยาม Done
Phase 1 — Live Board อ่าน Ticket จริง, map คอลัมน์, filter พื้นฐาน, Claim, เปิด drawer ข้อมูลจริง, รูปแนบ, guest read-only / IT write guard เคสจาก portal โผล่บนกระดานและ claim ได้
Phase 2 — Collaboration Worklogs = timeline/notes, multi-assignee + role, transfer, refresh จริง ทีมทำงานบนเคสเดียวกันได้โดยมีประวัติ
Phase 3 — Confirm Close Email token close/reopen ตาม ADR 0003, คอลัมน์ pending_user มีความหมายจริง Closed Ticket เกิดจาก user confirm
Phase 4 — Quick Log สร้าง QUICK_TICKET + approval policy บันทึกงานหน้างานไม่หาย
Phase 5 — Work Cycle ตารางรอบงาน, carryover tag, cron close, เชื่อม IT Overview ตัดรอบอัตโนมัติตาม ADR 0001
Group view / Filters ขั้นสูง / Progress % อัตโนมัติ — จัดเป็น nice-to-have หลังเฟส 1–2

12. ความเสี่ยงและข้อควรระวัง

  • Semantic mismatch: คำว่า Resolved ใน UI ≠ Closed Ticket ในโดเมน — ถ้าไม่เคลียร์จะทำสถิติพัง
  • Security: ตอนนี้ ticket write API เปิดกว้าง; พอเปิดกระดานจริงต้องใส่ auth ให้ครบ
  • Realtime: หลายคนเคลมพร้อมกัน — ควรมี optimistic concurrency หรือ unique claim rule
  • Email dependency: เฟส confirm close พึ่งเมลองค์กร; ต้องมี resent token / เคสเมลเด้ง
  • Scope creep: พยายามทำ work cycle + email + quick log พร้อมกันจะช้ามาก

13. คำถามที่ยังไม่เคลียร์ — รบกวนตอบทีละข้อ

ตอบเป็น Q1, Q2, … ได้เลย แล้วค่อยเริ่มลงมือตามคำตอบ

  1. Q1. ยอมรับแผนเฟสแบบ Hybrid (เฟส 1 Live Board ก่อน) หรือต้องการทำให้ครบ ADR (Work Cycle + Email close) ก่อนเปิดใช้กระดานจริง?
  2. Q2. เมื่อ IT กดปุ่มแบบ “Approve and close / Resolve” ใน drawer วันนี้ ควรถือว่าเป็นการ (ก) ย้ายไปรอผู้ใช้ยืนยัน, (ข) ปิดเคสทันทีในระบบ, หรือ (ค) อื่น ๆ?
  3. Q3. คอลัมน์ pending_user หมายถึงอะไรแน่? รอ user ทดสอบหลัง IT แก้ / รอ approve Quick Ticket / รอ email confirm / อย่างอื่น?
  4. Q4. ควรเพิ่มสถานะใน DB ใหม่ (เช่น PENDING_USER) หรือ map ทับ PENDING_APPROVAL / RESOLVED ที่มีอยู่?
  5. Q5. กระดานเฟส 1 ควรโชว์เฉพาะเคส OPEN/IN_PROGRESS/… ที่ยังไม่ CLOSED ทั้งระบบ หรือต้องผูก “รอบงานปัจจุบัน” ทันที?
  6. Q6. Progress % บนการ์ด: เก็บใน DB ให้ IT กรอก / คำนวณอัตโนมัติ / เอาออกจาก UI ชั่วคราว?
  7. Q7. ต้องการบทบาท Lead / Collaborator จริงใน schema หรือพอเป็นรายชื่อผู้รับผิดชอบเท่ากันไปก่อน?
  8. Q8. ใครกด Claim ได้บ้าง? IT Staff ทุกคน / เฉพาะที่ว่าง / มีกฎไม่ให้แย่งเคสที่มี lead แล้ว?
  9. Q9. Quick Log ควร (ก) สร้างเคสขึ้นกระดาน, (ข) บันทึกแล้วปิดทันทีโดยไม่โชว์คอลัมน์, หรือ (ค) ต้องให้ Supervisor อนุมัติก่อนนับ?
  10. Q10. Guest ที่เปิด /it ควรมองเห็นข้อมูลผู้แจ้ง (ชื่อ/อีเมล/เบอร์ต่อ) เต็ม ๆ ได้ไหม หรือต้องปกปิดบางส่วน?
  11. Q11. ปุ่ม Group view และ Filters ขั้นสูงใน UI: ทำในเฟส 1 หรือเลื่อนได้?
  12. Q12. Timeline ควรมาจากอะไรเป็นหลัก: Worklog อย่างเดียว / AuditLog / Event log แยก / รวมหลายแหล่ง?
  13. Q13. การย้ายการ์ดข้ามคอลัมน์ด้วยการลาก (drag-and-drop) ต้องมีในเฟสแรกไหม หรือคลิก + ปุ่มสถานะพอ?
  14. Q14. เคสที่สร้างจาก portal ก่อนหน้านี้ใน DB (ที่มีอยู่แล้ว) ต้องโผล่บนกระดานทั้งหมดทันทีเมื่อ wire เสร็จ ใช่หรือไม่?
