ภาพรวมก่อนเริ่ม Mindset

Architecture pattern คือ “ข้อตกลงเรื่องการจัดวางความรับผิดชอบ” ไม่ใช่ framework เฉพาะตัว และมักผสมกันได้ เช่น NestJS ที่เป็น Modular + แยก layer แบบ Controller → Service → Repository หรือระบบใหญ่ที่ใช้ DDD + Clean Architecture + Modular Monolith

คนมักสับสนระหว่าง logical layers (ชั้นในโค้ด) กับ physical tiers (เครื่อง/เซิร์ฟเวอร์ที่ deploy แยก) — ทั้งสองเกี่ยวข้องกัน แต่ไม่ใช่คำเดียวกัน

1. Modular Architecture โครงสร้างแพ็กเกจ

แบ่งระบบเป็น โมดูล (module / package) ที่แต่ละก้อนมีขอบเขตชัดเจน มี API สาธารณะของตัวเอง และซ่อนรายละเอียดภายใน เป้าหมายคือให้ทีมแก้/ขยายฟีเจอร์โดยไม่ต้องรู้ทั้งระบบ

ใน NestJS, Angular, หรือ monorepo ที่แยก apps/* + packages/* มักใช้แนวนี้เป็นพื้นฐาน — โมดูลอาจตัดตาม feature (Tickets, Auth) หรือตาม shared capability (Mail, Database)

ตัวอย่างโครงสร้างโฟลเดอร์ (feature modules)

apps/api/src/
├── tickets/
│   ├── tickets.module.ts
│   ├── tickets.controller.ts
│   ├── tickets.service.ts
│   └── dto/
├── auth/
│   ├── auth.module.ts
│   └── ...
├── users/
└── shared/                 ← ใช้ร่วม (ไม่ใช่ business ของใครคนใดคนหนึ่ง)
    ├── mail/
    └── prisma/

ข้อสังเกต / ข้อดี

  • สเกลทีมได้ดี — คนละโมดูลทำงานคู่ขนาน
  • ขอบเขตชัด → review และ ownership ชัด
  • เตรียมทางไป Modular Monolith หรือ Microservice ได้

ข้อพลาดที่พบบ่อย

  • โมดูล import กันมั่ว → กลายเป็น “spaghetti modules”
  • ยัดทุกอย่างลง shared/ จน shared เป็นถังขยะ
  • แยกโมดูลตาม technical layer อย่างเดียว แล้ว feature กระจาย
มาตรฐานทีม: โมดูลหนึ่งควรมี “สัญญา” ชัด — export อะไรได้, อะไรห้าม import ข้าม (เช่น ห้าม Tickets ไปเรียก repository ภายใน Users โดยตรง)

2. Layered / N-Tier Architecture ชั้นความรับผิดชอบ

Layered Architecture (บางคนเรียก Tiered) จัดโค้ดเป็นชั้นซ้อนกัน แต่ละชั้นเรียกได้เฉพาะชั้นที่อยู่ “ข้างล่าง” (หรือข้างใน) ตามกฎที่ทีมตกลง

N-Tier มักหมายถึงการแยก ทางกายภาพ ด้วย เช่น Web server / Application server / Database server (2-tier, 3-tier, …) ในชีวิตจริงทีมมักพูด “3-tier” หมายถึง Presentation + Business + Data ทั้งแบบ logical และ physical ปนกัน — ควรถามให้ชัดว่าหมายถึงชั้นในโค้ดหรือเครื่องแยก

ชั้นคลาสสิก: Presentation → Application / Business → Persistence / Data

Logical layers (ในโปรเจกต์)

Presentation — Controller / UI / API
↓ เรียกได้
Business — Service / Use case
↓ เรียกได้
Persistence — Repository / ORM
↓ เรียกได้
Database / External systems

Physical tiers (deploy)

Tier 1 — Browser / Mobile client
↓ network
Tier 2 — API / App server
↓ network
Tier 3 — Database server

Layer ในโค้ดอาจอยู่ครบใน Tier 2 ก้อนเดียวก็ได้

ตัวอย่างโฟลว์ (Helpdesk)

// Presentation
POST /tickets  →  TicketsController.create()
       ↓
// Business
TicketsService.createTicket(dto)  // กฎ: ใครเปิดได้, SLA, ฯลฯ
       ↓
// Persistence
TicketRepository.save(entity)
       ↓
PostgreSQL

ข้อสังเกต / ข้อดี

  • เรียนรู้ง่าย — มือใหม่เข้าใจเร็ว
  • มาตรฐานใน enterprise / CRUD apps มานาน
  • แยก UI ออกจาก business ได้ระดับหนึ่ง

ข้อพลาดที่พบบ่อย

  • Fat service / Anemic domain — logic กองใน service ยาว ๆ
  • ชั้นบนข้ามชั้นกลางไปคุย DB โดยตรง
  • เปลี่ยน DB / UI แล้วยัง “รั่ว” รายละเอียดขึ้นบน
  • ทุก feature ผ่านชั้นเดียวกัน → ไฟล์ service บวม
อย่าสับสนคำ: “Layered” ≠ “Clean” Layered อนุญาตให้ business พึ่ง ORM ได้บ่อย ๆ ส่วน Clean/Hexagonal จะบังคับให้ dependency ชี้เข้าหา domain มากกว่า

3. Domain-Driven Design (DDD) ภาษาธุรกิจ

DDD ไม่ใช่แค่โฟลเดอร์ แต่เป็นแนวคิดให้โมเดลซอฟต์แวร์สะท้อนโดเมนธุรกิจ โดยใช้ภาษาเดียวกันกับผู้เชี่ยวชาญธุรกิจ (Ubiquitous Language) และแบ่งระบบตามขอบเขตความหมาย (Bounded Context)

มีสองระดับ: Strategic (แบ่งโลกธุรกิจ) และ Tactical (เครื่องมือในโค้ด: Entity, Value Object, Aggregate, Domain Event, …)

คำศัพท์ tactical ที่ควรรู้

คำ ความหมายสั้น ๆ ตัวอย่าง Helpdesk
Entity มีตัวตนต่อเนื่อง มี identity Ticket, User
Value Object ไม่มี identity แยก — เท่ากันถ้าค่าเท่ากัน Email, Priority, TicketStatus
Aggregate คลัสเตอร์ที่ consistency ต้องผ่าน root Ticket + comments ภายใต้กฎเดียวกัน
Domain Event สิ่งที่ “เกิดแล้ว” ในโดเมน TicketClosed, TicketReopened
Repository โหลด/เก็บ aggregate — ไม่ใช่ CRUD ทุกตาราง TicketRepository.findById()
Bounded Context ขอบเขตที่คำศัพท์มีความหมายเดียว “User” ใน Auth ≠ “Requester” ใน Ticket

ตัวอย่างแนวคิด (ไม่ต้อง framework พิเศษ)

// Domain รู้กฎ — ไม่รู้ว่าใช้ Prisma หรือ HTTP
class Ticket {
  close(actor: Agent) {
    if (this.status === 'CLOSED') throw ...
    this.status = 'CLOSED'
    this.record(new TicketClosed(this.id, actor.id))
  }
}

ข้อสังเกต / ข้อดี

  • เหมาะกับธุรกิจซับซ้อน มีกฎเยอะ
  • ลดการคุยคนละภาษา (“status” หมายความว่าอะไร)
  • จับคู่กับ Clean/Hexagonal ได้ดี

ข้อพลาดที่พบบ่อย

  • ใส่ Entity/VO เต็มโปรเจกต์ CRUD เล็ก ๆ → over-engineering
  • เรียก DDD แต่ logic ยังอยู่ใน service + DTO
  • ลืม Strategic — โฟกัสแต่ folder ชื่อ domain/
เมื่อไหร่ใช้หนัก: เมื่อกฎธุรกิจเปลี่ยนบ่อยและผิดพลาดมีผลสูง ถ้าเป็น admin CRUD ง่าย ๆ Layered + Modular อาจพอ

4. Clean Architecture / Hexagonal Architecture Dependency Rule

ทั้งสองแนวคิดใกล้กันมาก: ธุรกิจอยู่ตรงกลาง ส่วน UI, DB, Queue, Email เป็นรายละเอียดที่ “เสียบ” เข้ามาทีหลัง

  • Hexagonal (Ports & Adapters) — โดเมนมี port (interface) และโลกภายนอกเป็น adapter (HTTP controller, Prisma adapter, SMTP adapter)
  • Clean Architecture (Uncle Bob) — วงแหวนของชั้น โดย dependency ชี้เข้าในเสมอ (Dependency Rule) ชั้นในไม่รู้จัก framework / DB

โครงสร้างโฟลเดอร์แบบที่เจอบ่อย

src/
├── domain/                 ← entities, value objects, domain errors
├── application/            ← use cases / ports (interfaces)
│   ├── ports/
│   │   ├── ticket.repository.ts
│   │   └── mailer.ts
│   └── use-cases/
│       └── close-ticket.ts
└── infrastructure/         ← adapters จริง
    ├── http/
    ├── persistence/prisma/
    └── mail/smtp/

ทิศทาง dependency ที่ถูกต้อง

// application/ports/ticket.repository.ts  (interface อยู่ชั้นใน)
interface TicketRepository {
  findById(id: TicketId): Promise<Ticket | null>
  save(ticket: Ticket): Promise<void>
}

// infrastructure/... implements interface ด้านบน
// domain / use-case ไม่ import Prisma ตรง ๆ

ข้อสังเกต / ข้อดี

  • ทดสอบ use case โดย mock port ได้ง่าย
  • เปลี่ยน DB / UI โดยไม่ทำลายกฎธุรกิจ
  • สื่อสารกับทีมอาวุโสได้ตรงคำศัพท์ industry

ข้อพลาดที่พบบ่อย

  • สร้าง interface ทุกอย่างโดยไม่จำเป็น → ceremony สูง
  • use case กลายเป็น proxy บาง ๆ ที่แค่เรียก repository
  • ลาก framework types (เช่น Nest @Injectable) เข้า domain
Onion Architecture เป็นญาติสนิทของ Clean — วงแหวน Domain → Application → Infrastructure เช่นกัน ถ้าใครพูด Onion ให้คิดภาพ Clean/Hexagonal ได้เลย

5. รูปแบบอื่นที่นิยมและควรรู้ Must-know

ไม่ต้องเก่งทุกแบบ แต่ควรรู้จักชื่อและความหมายเมื่อทีมพูดถึง

Modular Monolith

ระบบก้อนเดียว (deploy ร่วม) แต่ภายในแบ่งโมดูลขอบเขตชัด — ทางสายกลางก่อนแตกเป็น microservice

นิยมสูงในทีมโต

Microservices

แยกบริการตาม business capability deploy อิสระ ได้ isolation แต่แลกด้วยเครือข่าย, data consistency, ops

กระจายระบบ

Vertical Slice / Feature Slice

จัดโค้ดตาม use case แนวตั้ง (CreateTicket รวม handler+dto+logic) แทนการตัดตาม layer แนวนอนอย่างเดียว

ลดไฟล์กระโดด

MVC / MVP / MVVM

แพทเทิร์นฝั่ง UI: แยก View ออกจาก state/logic (React มักเป็น component + hooks / store มากกว่า MVC ตรงตัว)

Frontend

CQRS

แยกโมเดลอ่าน (Query) กับเขียน (Command) ใช้เมื่อหน้าจออ่านซับซ้อนหรือ throughput สูง — อย่าใช้ทุก CRUD

อ่าน/เขียนแยก

Event-Driven Architecture

บริการสื่อสารผ่าน event/message (queue, bus) ลด coupling ด้านเวลา แต่ต้องออกแบบ idempotency / ordering

Async / Integration

Event Sourcing

เก็บลำดับเหตุการณ์เป็นแหล่งความจริง แล้ว derive state ทรงพลังแต่ซับซ้อน — มักคู่กับ CQRS

Advanced

SOA / API Gateway

บริการถูกเปิดผ่าน contract (API) รวมศูนย์ทางเข้า พบบ่อยในองค์กรที่มีระบบเดิมหลายตัว

Enterprise
ที่เจอในโปรเจกต์สมัยใหม่บ่อยสุด: Modular (หรือ Modular Monolith) + Layered เบา ๆ ภายในโมดูล และค่อยดึง DDD/Clean เข้ามาเฉพาะ bounded context ที่ซับซ้อน

6. ตารางเปรียบเทียบสั้น ๆ

แนวทาง ตัดระบบตาม จุดแข็ง ระวัง
Modular ขอบเขตโมดูล / feature ownership, สเกลทีม dependency ระหว่างโมดูล
Layered / N-Tier ชั้น technical เรียบง่าย เป็นมาตรฐาน service อ้วน, ข้ามชั้น
DDD ภาษาและขอบเขตโดเมน ธุรกิจซับซ้อน overkill ถ้าโดเมนง่าย
Clean / Hexagonal ทิศทาง dependency ทดสอบ, เปลี่ยน infra boilerplate
Vertical Slice use case แนวตั้ง เปลี่ยน feature เร็ว ซ้ำโค้ดข้าม slice
Microservices บริการ + deploy อิสระ สเกลแยก กระจายความซับซ้อน

7. คุยกับทีมยังไงให้เป็นมาตรฐาน

ประโยคที่ใช้อธิบายงานได้ทันที

  • “โมดูลนี้เป็น bounded context ของ Ticketing ไม่ปน Identity”
  • “Controller เป็น adapter — กฎปิดตั๋วอยู่ใน domain/use case”
  • “อย่าให้ presentation พึ่ง Prisma โดยตรง ผ่าน repository port”
  • “เราเป็น modular monolith ตอนนี้ ยังไม่แยก service”
  • “อันนี้เป็น vertical slice ของ Close Ticket ไม่ใช่ shared util ทั่วไป”

สิ่งที่โปรเฟสชันนัลทำ

  • ตั้งชื่อโฟลเดอร์/คลาสให้สะท้อนความรับผิดชอบจริง
  • เขียน ADR สั้น ๆ เมื่อเลือก architecture สำคัญ
  • ยอมรับ hybrid — ไม่ศาสนา pattern เดียว
  • ประเมินความซับซ้อนของโดเมนก่อนเลือกของหนัก

สิ่งที่ควรเลี่ยง

  • ยก Clean Architecture ทั้งก้อนมาใส่ CRUD นับสิบตาราง
  • เรียกชื่อ pattern แต่โครงสร้างจริงไม่ตรง
  • แยก microservice เพราะ “ฟังดูเท่” โดยไม่มีขอบเขตชัด
  • ไม่มีกฎ import / boundary แล้วทะเลาะตอน review
สรุปหนึ่งประโยค: เริ่มจาก Modular + Layered ที่วินัยดี → เติม DDD / Clean ที่จุดที่ธุรกิจซับซ้อน → ค่อยคิด Microservices / Event-driven เมื่อมีเหตุผลด้านสเกลและทีม
